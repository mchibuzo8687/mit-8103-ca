## 1. Replication strategy

### 1.1 Roles

| Replica role | Mode | CareLink use |
|--------------|------|--------------|
| Synchronous standby | Sync WAL / quorum commit in second AZ | Survive AZ failure; promote to primary |
| Asynchronous read replica | Async streaming replication | Cross-branch history, revenue reports, lab SLA dashboards |
| Logical publication (optional) | Logical replication of selected tables | Feed reporting warehouse or MongoDB change-capture bridge |

### 1.2 What is replicated

**Physical / streaming replication** copies the entire CareLink database: all Portfolio 1 tables. That preserves foreign keys (`appointment` → `patient` / `staff` / `branch`, `payment` → `service`, etc.) without application-level join fan-out across nodes.

### 1.3 Write vs read traffic

```text
Writes (must hit PRIMARY)
  - INSERT/UPDATE appointment, encounter, diagnosis, prescription,
    lab_order, payment, patient, staff

Reads that prefer PRIMARY
  - Confirm slot before booking UI commit
  - Payment status immediately after card capture
  - “Is this doctor free in the next 30 minutes?”

Reads that may use ASYNC REPLICA
  - Patient longitudinal history across Ikeja + VI
  - Manager revenue-by-branch (Portfolio 2 Q3 style)
  - Lab turnaround aggregates
```

### 1.4 Replication lag policy

| Metric | Target | Action if breached |
|--------|--------|--------------------|
| Sync standby apply lag | ≈ 0 (sync) | Block/fail primary commit if standby unreachable (HA trade-off) |
| Async replica lag | &lt; 5 seconds typical; alert at 30s | History UI falls back to primary for a single patient lookup; dashboards show “data delayed” |

## 2. Sharding / partitioning by branch

### 2.1 Why branch is the natural key

Almost every CareLink operational query from Portfolio 2 filters or groups by branch:

- Daily schedule: `WHERE branch_id = :ikeja AND scheduled_at::date = CURRENT_DATE`  
- Revenue by branch  
- Staff assignment via `staff.branch_id`

Partitioning (and later sharding) on **`branch_id`** keeps each clinic’s hot working set together, improves partition pruning, and maps cleanly to organisational growth (add partition / shard per new branch).

### 2.2 Declarative partitioning design (PostgreSQL)

Conceptual evolution from the Portfolio 1 monolithic tables (illustrative — not applied to Portfolio 1 files):

```sql
-- Illustrative: partition appointment by branch_id
CREATE TABLE appointment (
    appointment_id   BIGINT GENERATED BY DEFAULT AS IDENTITY,
    patient_id       INTEGER      NOT NULL,
    doctor_id        INTEGER      NOT NULL,
    branch_id        INTEGER      NOT NULL,
    scheduled_at     TIMESTAMPTZ  NOT NULL,
    duration_minutes INTEGER      NOT NULL DEFAULT 30,
    status           VARCHAR(20)  NOT NULL DEFAULT 'booked',
    reason           VARCHAR(255),
    created_at       TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at       TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    PRIMARY KEY (appointment_id, branch_id),
    UNIQUE (doctor_id, scheduled_at, branch_id)  -- see note below
) PARTITION BY LIST (branch_id);

CREATE TABLE appointment_ikeja PARTITION OF appointment
    FOR VALUES IN (1);   -- CL-IKE

CREATE TABLE appointment_vi PARTITION OF appointment
    FOR VALUES IN (2);   -- CL-VI

CREATE TABLE appointment_default PARTITION OF appointment DEFAULT;
```

**Unique constraint note:** PostgreSQL requires partition keys to be included in unique indexes on partitioned tables. CareLink still enforces “one doctor, one timestamp” **application-wide** by either:

- keeping a small global `doctor_slot_lock` table unpartitioned, or  
- ensuring doctors are primarily assigned to one branch (true for seed data) and validating cross-branch locum bookings at the API layer.

Child clinical tables can:

1. **Inherit locality** by always joining through `appointment.branch_id`, or  
2. **Carry `branch_id`** redundantly on `encounter` / `payment` for direct pruning (controlled denormalisation acceptable in distributed designs).

### 2.3 Partitioning vs sharding

| Technique | Scope | When CareLink uses it |
|-----------|-------|------------------------|
| **Partitioning** (single cluster) | One PostgreSQL instance, multiple table partitions | Current design: Ikeja / VI partitions, multi-AZ HA |
| **Sharding** (multiple nodes) | Rows distributed across nodes by `branch_id` | Future: many branches / heavy write volume; Citus or similar with `branch_id` distribution key |

**Patient table** should remain a **reference / non-sharded** (or duplicated) dimension so every shard can resolve `patient_id` without cross-shard chatter on every booking.

### 2.4 Example shard key mapping

| `branch_code` | `branch_id` | Partition / future shard |
|---------------|-------------|--------------------------|
| CL-IKE | 1 | `appointment_ikeja` / shard-ikeja |
| CL-VI | 2 | `appointment_vi` / shard-vi |
| (future) CL-ABJ | 3 | new LIST partition / new shard |

## 3. CAP theorem applied to CareLink

In a partition between a branch site and the cloud primary:

| Choice | Meaning for CareLink | Verdict |
|--------|----------------------|---------|
| **CP** (Consistency + Partition tolerance) | Refuse new bookings/payments if primary unreachable | **Chosen for writes** |
| **AP** (Availability + Partition tolerance) | Accept local bookings that may conflict later | Rejected for appointments/payments — conflicts violate clinical schedule integrity and billing |
| Soft **AP** for reads | Serve last-known schedule from cache/replica | Acceptable for display-only |

**Rationale:** Double-booking a doctor (`uq_doctor_slot`) or recording two “completed” payments for the same visit under split-brain is clinically and financially unacceptable. Temporary inability to book during an outage is preferable to silent inconsistency.

## 4. PACELC refinement

PACELC extends CAP: if Partition → choose A or C; **Else** (normal operation) choose Latency or Consistency.

| Situation | CareLink preference | Practice |
|-----------|---------------------|----------|
| **P**artition | **C**onsistency | Quorum/sync commit to standby; fail writes if HA cannot acknowledge |
| **E**lse (normal) | Balance **L** and **C** | Writes: sync to standby (slight latency for durability). Heavy reads: async replicas (lower latency, slight staleness) |

### Per-operation PACELC profile

| Operation | Under partition | Under normal load |
|-----------|-----------------|-------------------|
| Book appointment | Refuse (C) | Confirm on primary (C over L) |
| Take payment | Refuse (C) | Primary commit (C) |
| View cross-branch history | Stale cache OK (A-ish) | Async replica (L over C) |
| Manager analytics | Offline dashboard OK | Async replica (L) |

## 5. Consistency models in practice

| Model | CareLink application |
|-------|----------------------|
| Strong / linearizable writes | Appointment status transitions, payments (aligns with Portfolio 3 transactions) |
| Read-your-writes | After booking, reception UI reads from primary (or session sticky) so the new slot appears immediately |
| Bounded staleness | History pages tolerate replica lag with monitoring |
| Eventual (document store) | Optional MongoDB clinical notes converge after encounter insert |

## 6. Interaction with Portfolio 3 concurrency controls

Distributed placement does **not** replace local concurrency control:

- `BEGIN` … `COMMIT` visit workflows still run on the primary.  
- Isolation (READ COMMITTED / stronger where needed) still prevents lost updates on payment status.  
- Replication only **propagates** committed results; it does not weaken `uq_doctor_slot` or FK integrity on the primary.

## 7. Optional MongoDB Atlas replication (Portfolio 4 link)

If clinical notes move to documents:

- Atlas replica set provides HA for the document tier.  
- Relational `encounter_id` remains the join key.  
- Document tier can be **AP-leaning** (notes still editable if slightly delayed) while booking stays **CP** on PostgreSQL.

## 8. Summary table

| Mechanism | CareLink decision |
|-----------|-------------------|
| Sync replication | Multi-AZ failover for primary OLTP |
| Async replication | History & analytics read scale-out |
| Partitioning | `LIST (branch_id)` on high-volume operational tables |
| Future sharding | Distribute by `branch_id`; keep `patient` global/reference |
| CAP | CP for booking & payments |
| PACELC | C under partition; sync durability + async read latency when healthy |
